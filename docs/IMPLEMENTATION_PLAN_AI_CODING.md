适用范围：草稿恢复、事件顺序、历史编辑、数据一致性及发布验收。

## 1. 交付目标

用户修改任意一条支持编辑的历史记录后，记录保持原来的逻辑位置，后续状态重新计算。保存失败时，已有有效记录和用户输入仍然保留。

本轮支持编辑组队提案、组队投票和任务结果。继续使用现有 Kotlin、Compose、Room 和手动依赖注入架构。

完成标准：

- 编辑对象由明确的事件 ID 定位，能够编辑早期任务和同一任务的不同提案。
- 修订在同一事务内完成，原事件与替代事件保留审计关系。
- 时间线、指定时间点复盘、首页状态和导出结果使用一致的事件顺序。
- 私人信息、未知信息和现场观察结果的既有语义得到保留。
- 有自动化测试结果、真机验收记录及可定位的 APK 产物。

## 3. 执行顺序

依赖顺序：A 草稿恢复 → B 逻辑顺序切换 → C 界面编辑 → D 完整验证 → E 文档与发布准备。

各阶段完成后先运行相关测试；没有解释清楚的失败时继续定位，不能通过删除测试或修改无关业务期望值推进。不同阶段可以分别形成可审查差异，对外发布时合并交付完整能力。

### A. 完成草稿恢复并固定基线

**实施内容**

1. 审阅已有 RT-006 实现与测试，列出保留和补充的内容。
2. 草稿恢复由异步读取完成；使用输入版本号或用户操作标记，保证恢复结果不会覆盖用户后续输入。
3. 将“输入后清空”视为有效用户操作，不能仅用“当前草稿等于空草稿”判断是否允许覆盖。
4. 草稿读取失败或 JSON 损坏时，页面继续可用；记录必要诊断信息。恢复本身不触发再次保存。
5. 检查草稿是否带有任务、提案上下文；在阶段 C 加入编辑目标后，旧格式草稿仍需安全兼容。

**主要文件**：`feature/record/RecordViewModel.kt`、`RecordUiState.kt`、草稿编解码及对应测试。

**完成标准**：页面重建能恢复已保存草稿；读取延迟期间的输入与清空操作均不会被覆盖；损坏草稿不阻断页面。记录本阶段实测基线和现有未提交改动的处理情况。

### B. 完成逻辑顺序切换与历史状态刷新

**顺序契约**

- 数据库列 `occurredOrder` 保留为写入序号，用于分配和审计。
- `logicalPosition` 表示历史逻辑位置，同一事件的修订版本继承原位置。
- `revisionSeq` 沿用现有实现：原始版本为 0，每次修订加 1。
- 领域事件的 `occurredOrder` 映射到 `logicalPosition`；`upTo` 表示逻辑位置上界。
- 有效位置允许因撤销出现空缺，追加时不复用已使用位置。

**实施内容**

1. `EventCodec.decode` 切换到逻辑位置；同步注释。
2. DAO 的事件排序、上界过滤和参数命名使用逻辑位置，审计读取保留全部版本。
3. 仓储输出有效事件时，在解码前按逻辑位置处理重复有效版本：版本号大者优先；相同版本按已有方案的确定顺序选择。保留异常日志和原始数据库行。
4. 同步 `MatchBundle`、重放与时间线的契约。重放引擎已有实现满足契约时，仅调整注释及测试。
5. 审计 `AppendResult.occurredOrder`、撤销返回值和全部消费方，明确哪些是写入序号、哪些是逻辑位置，修正需要表达逻辑位置的返回路径。
6. 实现一次性旧对局状态重算：后台逐局复用现有重放逻辑，保留 `revealedAt`；全部成功后写入顺序模型版本标记，中断后允许重试。
7. 刷新与用户写入复用事务边界，避免旧快照覆盖新状态。重算不应无故改变对局最近活动时间或首页排序；需要调整投影更新方法时同步验证。
8. 验证旧版及新版 JSON 导入、有效事件导出；不引入额外数据库结构变更。

**主要文件**：`core/database/EventCodec.kt`、`dao/MatchEventDao.kt`、`core/data/RoomMatchRepository.kt`、`MatchBundle.kt`、设置仓储与应用初始化，以及对应测试。

**完成标准**：五条事件中修订第三条后，顺序为“1、2、第三条新版本、4、5”；`upTo=3` 包含该新版本，`upTo=2` 不包含；再次修订不改变位置。旧对局无需新增记录即可完成状态刷新，首页与复盘最终一致。

### C. 界面接入明确目标和事务修订

**实施内容**

1. 点击历史记录时传入 `eventId`。ViewModel 根据 ID 加载事件，而不是仅根据事件类型打开当前轮弹窗。
2. 增加明确的新增与编辑状态。编辑上下文至少包含目标 ID、事件类型、原任务号和原提案号；编辑弹窗显示并加载目标事件原值。
3. 编辑字段与新增草稿分开管理。恢复编辑草稿时核实目标仍有效，失效时保留输入并提示重新加载。
4. 新增调用 `appendEvent`；编辑调用 `reviseEvent`。移除编辑流程中的“先撤回、后追加”。
5. 仓储事务内重新核实目标对局、类型和有效状态，再撤销旧版本、插入新版本并刷新状态。DAO 撤销条件包含目标仍有效的检查，防止并发修订形成两个有效版本。
6. 同一页面保存时防止重复提交；仓储仍承担最终并发保护。统一处理异常和返回值错误，取消协程时正确传播取消。
7. 保存成功后再关闭弹窗和清理对应草稿；保存失败保留输入、旧有效事件及重试入口。
8. 修改投票后重算规则结论。与已有现场通过／否决记录冲突时提示复核，不静默改写现场事实。

**主要文件**：`RecordScreen.kt`、`RecordUiState.kt`、`RecordViewModel.kt`、相关 Sheet、仓储与 DAO、测试替身及测试。

**完成标准**：修改第一轮不会写入当前轮；同轮不同提案分别定位；取消不写库；模拟插入失败后旧事件仍有效；同一目标竞争修订最多一次成功，另一请求得到可理解的冲突提示。
